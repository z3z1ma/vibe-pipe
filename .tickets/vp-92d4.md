# Make sql_asset executable + integrate exports

## Objective alignment
SQL assets are a core declarative abstraction. Right now `sql_asset` exists in code but is not wired into execution or exported, which breaks documented workflows and undermines cohesiveness.

## Scope
- Implement a real execution path for SQL assets (render template, validate SQL, execute via connector or IO manager).
- Export `sql_asset` from `src/vibe_piper/__init__.py` (remove TODO stub).
- Define a minimal contract for dependency substitution in SQL templates.
- Add tests covering SQL rendering, dependency mapping, and execution using a stub connector.

## Non-goals
- Full SQL engine/optimizer or advanced lineage parsing.
- UI/monitoring integration.
- Distributed execution.

## Implementation plan
1. In `src/vibe_piper/sql_assets.py`, update `_create_asset_from_sql_operator` to attach an Operator that:
   - Builds a render context with dependency names (default: each dependency maps to itself unless overridden in config).
   - Calls `render_sql_template` + `validate_sql`.
   - Executes via `execute_sql_query` using a connector provided in config (e.g., `config["connector"]`) or context metadata (documented fallback).
2. Add a small helper (e.g., `_resolve_sql_dependencies`) to support `config["relations"]` mapping of asset name -> table name.
3. Update `src/vibe_piper/__init__.py` to import `sql_asset` (and keep optional deps guardrails).
4. Add tests in `tests/test_sql_assets.py` (new) using a stub connector with a `query` method to assert rendered SQL + params.
5. Update `docs/sql_assets.md` to document the execution contract (connector requirement and dependency mapping).

## Acceptance criteria
- `@sql_asset` returns an Asset with an operator that executes and returns query results.
- SQL template rendering replaces `{{ asset }}` dependencies with relation names (default asset name, override via config).
- `vibe_piper.sql_asset` is exported and not None when sql_assets.py is importable.
- Tests pass for rendering, validation, and execution flow.

## Verification
- `uv run pytest tests/test_sql_assets.py -q`
- `uv run pytest tests/test_public_api.py -q`

## Risks / edge cases
- Template rendering currently uses StrictUndefined; missing dependency variables must be injected to avoid runtime errors.
- Optional deps (jinja2, sqlglot) should fail with clear ImportError messages.
- Connector contract must be clear (method name and return type).

## Dependencies
- Depends on vp-3fcc if dependency storage is needed for graph building (not strictly required for execution).
