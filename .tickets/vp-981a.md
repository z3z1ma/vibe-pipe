# Sprint prep: The Great Pruning

Objective:
We are creating the most robust python based declarative data pipeline, integration, quality, transformation, activation library ever created. Our zen is simplicity and maximizing expressivity and composability. Now we need to focus on cleaning up dead code, cleaning up cruft, bloat, useless features, and so on. We need to streamline and hone in now that we have defined our API. We need completely coherent documentation. Coherent optimized readme based on the final state of the code. Useless files removed. Etc etc

## Sprint Brief

- Objective restatement: Simplify Vibe Piper to a coherent, minimal, high-leverage core by pruning bloat, aligning the public API to the canonical abstraction contract, and ensuring documentation is accurate for the actual code.
- Sprint focus (2-5 words): API + Docs Pruning
- Why this sprint focus is the best next step: The codebase has a large public API surface, heavy optional subsystems (web/dashboard), and docs that do not map cleanly to canonical abstractions. Pruning the API and docs first creates a stable foundation for further work.
- Current state:
  - Existing tickets that matter: none prior to this sprint; new sprint tickets created (see Ticket Set).
  - Codebase state that matters:
    - `src/vibe_piper/__init__.py` exports 200+ symbols across core + optional features, increasing bloat risk.
    - Web/dashboard stack exists (`src/vibe_piper/web`, `src/vibe_piper/dashboard`, `frontend/`) with heavy deps in `pyproject.toml`.
    - README is very large, contains internal Loom notes, uses the wrong CLI name (`vibe-piper` instead of `vibepiper`), and references optional features without clear boundaries.
    - Docs are split between `docs/` markdown and `docs/source/` Sphinx, with stale or internal docs mixed in.
    - Git status: only untracked `.venv`.
- Risks + unknowns (and how we will resolve them):
  - Feature removal risk: web/dashboard removal may break CLI/tests; resolve by removing CLI hooks/tests and running unit tests.
  - Doc drift: docs may still reference removed symbols; resolve by updating README + Sphinx index after code pruning.
  - Optional features: keep/remove decisions can be contentious; resolve by aligning to `CORE_ABSTRACTION_CONTRACT.md` and explicit sprint scope.
